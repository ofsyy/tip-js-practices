## Эксперимент с очередями выполнения

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, F | A, B, C — синхронный код (B печатается внутри `async`-функции до первого `await`). D и E — микрозадачи в порядке постановки. F — таймер, следующая задача. |
| Фактический результат | `A: синхронный код` → `B: начало async-функции` → `C: конец синхронного кода` → `D: обработчик Promise` → `E: продолжение после await` → `F: задача таймера` | Совпало с прогнозом. |
| Прогноз после добавления `G` (свой `Promise.resolve().then`, зарегистрирован после вызова `demonstrateAwait()`) | A, B, C, D, E, G, F | `G` встаёт в очередь микрозадач третьим — после D и продолжения E, но раньше таймера. |
| Фактический результат с `G` | A, B, C, D, E, **G**, F | Совпало. |

- **Синхронный код:** A, B, C. `demonstrateAwait()` выполняется синхронно до `await null`.
- **Микрозадачи:** D (обработчик `then`, поставлен первым), E (продолжение после `await`, поставлено при вызове `demonstrateAwait`), G (собственный обработчик). Все выполняются сразу после окончания синхронного кода, в порядке постановки.
- **Таймер с задержкой `0`** — это отдельная задача: она выполняется только после того, как стек опустел **и** очередь микрозадач исчерпана. `0` означает «не раньше», а не «немедленно».
- Если удалить обработчик D, вывод станет A, B, C, E, G, F — относительный порядок остальных не меняется.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный API (не изменялся): маршруты, фильтры, ошибки, отладочные ответы. |
| `src/api-client.js` | Общий транспорт: `buildUrl`, `createApiClient` → `requestJson`, тайм-аут и отмена, единый `ApiError` с `kind`. О задачах ничего не знает. |
| `src/task-api.js` | Предметный клиент: маршруты `/tasks`, `/tasks/:id`, `/categories`, проверка фильтров до запроса и схемы ответа после, `loadInitialData` через `Promise.all`. |
| `src/variant.js` | Данные варианта: `variantNumber = 7`, `variantFilters = { q: "провер" }`. |
| `src/main.js` | Консольный сценарий: начальная загрузка, таблица задач, контрольная ошибка 404. |

**`fetchFn` передаётся в фабрику**, чтобы модульные проверки подставляли поддельный `fetch` (готовый `Response`, исключение, «вечный» запрос) без сети, а интеграционные — настоящий.

**HTTP- и сетевые ошибки разделены.** Вызов `fetchFn` обёрнут в отдельный `try`: туда попадает только отказ самого `fetch` (нет соединения, тайм-аут, отмена). Проверка `response.ok` и разбор тела — после этого блока, поэтому `ApiError` вида `http` не перехватывается и не превращается в `network`.

**JSON проверяется по контракту**, потому что `{"data":"не массив"}` — синтаксически верный JSON, но непригодный для приложения. `task-api.js` проверяет каждую задачу/категорию, уникальность id и `meta.total`.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | `new URL(baseUrl)`; только `http:`/`https:`, без `?` и `#`; иначе `TypeError` | client № 04 |
| Кодирование query-параметров | `url.searchParams.set(name, String(value))`; пропускаются только `undefined`, `null`, `""`; `false` и `0` сохраняются; на стыке `/` срезаются регулярными выражениями | client № 01–03, own № 01 (`q=провер` → `%D0%BF…`) |
| Заголовок `Accept` | `headers: { Accept: "application/json" }`, `method: "GET"` | client № 05 |
| Проверка `response.ok` | При `!response.ok` тело читается «мягко»; из `payload.error` берутся `message`, `code`, `details`; иначе сообщение `Сервер вернул HTTP <status>.` | client № 08, 09, 16 |
| Проверка `Content-Type` | После `ok` и `204`: заголовок должен содержать `application/json`, иначе `invalid-response` | client № 10, `/debug/text` |
| Разбор JSON | `await response.json()` в `try`; `SyntaxError` сохраняется как `cause` у `invalid-response` | client № 11, `/debug/invalid-json` |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)` передаётся в `fetch`; по умолчанию 2000 мс, можно задать на запрос | client № 14, own № 05 |
| Внешняя отмена | `AbortSignal.any([signal, timeoutSignal])`; при отказе первым проверяется `signal.aborted` → `aborted`, затем тайм-аут → `timeout`, иначе `network` | client № 15, own № 06 |

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач, id `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]` |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи, id `[4, 13, 34]`, `meta = { total: 3, filters: { completed: false, priority: "high", categoryId: null, q: "" } }` |
| `getTaskById(25)` | `{ id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 }` |
| `getCategories()` | `1 — Учёба`, `2 — Проект`, `3 — Организация` |
| `loadInitialData({ completed: false, priority: "high" })` | `{ tasks, categories, meta }`: 3 задачи, 3 категории, `meta` от запроса задач |

**Правила проверки.** Фильтры (до запроса): разрешены только `completed` (boolean), `priority` (`low/medium/high`), `categoryId` (положительное целое), `q` (строка, после `trim` до 100 символов, пустая не передаётся); иначе `TypeError` без сетевого запроса. Задача: положительный безопасный `id`, непустой `title` до 100 после `trim`, boolean `completed`, допустимый `priority`, положительный `categoryId`. Категория: положительный `id`, непустое `name` до 100. Коллекция: `data` — массив, все элементы по схеме, id уникальны, `meta.total === data.length`. Любое нарушение → `ApiError` с `kind: "invalid-response"`.

## Последовательная и параллельная загрузка

`npm run example:parallel`: два независимых запроса `/debug/delay?ms=300`.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 629.9 | 606.1 | 608.7 | ≈ сумма двух задержек: второй запрос начинается только после первого. |
| `Promise.all` | 304.7 | 307.3 | 305.8 | ≈ одна задержка: оба Promise созданы до общего `await`, сервер обрабатывает их одновременно. |

Ускорение здесь возникает не из-за `Promise.all` как такового, а потому что оба запроса **начаты** до ожидания; `Promise.all` лишь ждёт уже идущие операции. Искусственные задержки в `loadInitialData` не включены.

## Вывод

Реализованы общий HTTP-клиент (`buildUrl`, `requestJson`) и предметный модуль задач. Проходят все наборы: API 18/18, клиент 26/26, интеграция 13/13, собственные 7/7. Общий запрос вернул `[4, 13, 34]`, вариант 7 (`q: "провер"`) — `[7, 16]`, как в методичке. `Promise.all` с двумя запросами по 300 мс занимает ≈ 305 мс против ≈ 610 мс при последовательном ожидании.

Главное различие: **Promise** — это ещё не значение, его нужно дождаться (`await`). **HTTP-ошибка** — сервер ответил, но статус вне 2xx: `fetch` не отклоняется, клиент сам проверяет `response.ok`. **Сетевая ошибка** — ответа нет вовсе, отклоняется сам `fetch`. **Неверный ответ** — статус успешный, но тело не JSON, JSON повреждён или не соответствует схеме. **Тайм-аут** — запрос отменил собственный `AbortSignal.timeout`, **явная отмена** — сигнал вызывающего кода; оба различаются проверкой того, какой сигнал сработал.
