## 1. Цель работы

Связать браузерный интерфейс с HTTP API: получать и изменять задачи через `GET`, `POST`, `PATCH`, `DELETE`, показывать асинхронные состояния `loading` / `ready` / `empty` / `error` и не допускать, чтобы устаревший ответ перезаписал новый фильтр.

Результат: приложение в `practice-06` получает категории и задачи из учебного API, отправляет фильтры серверу в query-параметрах, создаёт, редактирует, переключает и удаляет задачи, после каждого изменения заново запрашивает список у сервера. Node.js-проверки — 70/70.

## 3. Реализация

### 3.1. HTTP-клиент

`src/api-client.js` перенесён из ПР5 (`buildUrl`, классификация ошибок, тайм-аут, внешняя отмена) и расширен:

- `requestJson(path, { method, query, body, signal, timeoutMs })`; разрешены только `GET`, `POST`, `PATCH`, `DELETE`, метод приводится к верхнему регистру (`"patch"` → `PATCH`), `PUT` — `TypeError` до запроса;
- `GET` с `body` отклоняется до сети;
- к каждому запросу добавляется `Accept: application/json`; при наличии `body` — `JSON.stringify(body)` и `Content-Type: application/json`, без тела этот заголовок **не** добавляется (лишний заголовок неверно описывает запрос и вызывает лишний CORS preflight);
- сначала проверяется `response.ok` (HTTP-ошибка сохраняет `status`, `code`, `details`, `url`), затем успешный `204` превращается в `null` **до** чтения тела, затем проверяются `Content-Type` и JSON;
- тайм-аут — `AbortSignal.timeout`, внешний сигнал объединяется через `AbortSignal.any`; виды ошибок `http`, `network`, `invalid-response`, `timeout`, `aborted` остаются различимыми, т. к. вызов `fetch` находится в отдельном `try`.

### 3.2. Доменный API

`src/task-api.js` — `createTaskApi(client)` возвращает:

| Метод | Запрос | Результат |
|---|---|---|
| `getTasks(filters, { signal })` | `GET /tasks?…` | `{ tasks, meta }` |
| `getTaskById(id, { signal })` | `GET /tasks/:id` | задача |
| `getCategories({ signal })` | `GET /categories` | массив категорий |
| `loadInitialData(filters, options)` | `Promise.all` двух запросов выше | `{ tasks, categories, meta }` |
| `createTask(draft, { signal })` | `POST /tasks`, тело `{ title, priority, categoryId }` | созданная задача (201) |
| `updateTask(id, changes, { signal })` | `PATCH /tasks/:id` с изменяемыми полями | обновлённая задача |
| `setTaskCompleted(id, completed, { signal })` | `PATCH /tasks/:id`, тело `{ completed }` | обновлённая задача |
| `deleteTask(id, { signal })` | `DELETE /tasks/:id` | строго `null` (204), тело → `invalid-response` |
| `resetDemoData({ signal })` | `POST /debug/reset` без тела | `{ reset: true, total }` |

Фильтры (`completed`, `priority`, `categoryId`, `q`) и `id` проверяются **до** запроса (`TypeError`). Схема проверяется **после** ответа: `readTask` для одиночной задачи (функция `isTask`), `readCollection` для коллекций (каждый элемент по `isTask`/`isCategory`, уникальность id, `meta.total === data.length`). Любое нарушение — `ApiError` вида `invalid-response`. В тело создания попадают только `title`, `priority`, `categoryId`: `id` и `completed` назначает сервер.

### 3.3. Состояния интерфейса

`src/app-controller.js` не обращается к `document`, а вызывает методы `view` (`dom-app.js`).

```text
load() → setListState("loading")  (aria-busy="true")
   ├─ ответ с задачами  → setTasks, setTotal → "ready"
   ├─ ответ, 0 задач    → setTotal(0)        → "empty" («По выбранным условиям задач нет.»)
   ├─ ошибка            → setTotal(0)        → "error" + messageForError + кнопка «Повторить»
   └─ aborted / устарел → ничего не меняется (отмена — не ошибка)
```

Первая загрузка — `loadInitialData` (задачи и категории параллельно). Пока категории не получены (например, первая загрузка упала), `refresh` / «Повторить» снова вызывает `loadInitialData`; после — только `getTasks` с текущими фильтрами.

### 3.4. Изменение данных

Все мутации идут через одну внутреннюю функцию `mutate(operation, message)`:

```text
setMutationPending(true) → запрос изменения → notify(success) → load() (GET с текущими фильтрами)
                         ↘ ошибка → notify(messageForError, "error")
finally: setMutationPending(false)
```

- **Создание / редактирование** — `submit(draft)`: `validateTaskDraft(draft, categories)` (название 1–100 после `trim`, приоритет, числовой `categoryId` из загруженного справочника). При ошибке — сообщения у полей и **никакого запроса**. Иначе `createTask` или `updateTask(editingId, value)`; при успехе форма возвращается в режим создания. Если сервер ответил `VALIDATION_ERROR`, его `details` выводятся у полей.
- **Смена статуса** — `toggleTask(id)`: текущий `completed` берётся из последнего ответа сервера, отправляется противоположный.
- **Удаление** — `deleteTask(id)` (после `confirm` в `dom-app.js`); если удалялась редактируемая задача — форма сбрасывается.
- **Сброс** — `resetData()`: `POST /debug/reset` и перезагрузка текущего фильтра.

Локальный массив задач никогда не изменяется «вручную»: интерфейс показывает только состояние, подтверждённое сервером.

### 3.5. Защита от устаревшего ответа

В `load()` два механизма:

1. **`AbortController`**: перед новой загрузкой `activeController?.abort()` — предыдущий `fetch` прерывается (в Network он виден как `(canceled)`), его ошибка `aborted` не показывается пользователю;
2. **номер загрузки** `loadSequence`: каждый запуск получает `sequence = ++loadSequence`, а результат применяется только если `sequence === loadSequence`. Это защищает даже если источник данных не отреагировал на сигнал (модульная проверка № 27: первый ответ приходит после второго и игнорируется).

## 6. Ответы на контрольные вопросы

1. **Почему `fetch` не отклоняет Promise при ответе 404?** Promise отклоняется только когда HTTP-ответ не получен (сеть, отмена, неверный URL). 404 — полноценный ответ сервера, поэтому статус нужно проверить самому (`response.ok`).
2. **Почему ответ 204 нельзя разбирать вызовом `response.json()`?** У 204 нет тела; `json()` от пустой строки бросает `SyntaxError`. Поэтому клиент возвращает `null` до чтения тела.
3. **Чем состояние `empty` отличается от `error`?** `empty` — запрос успешен, просто под условия ничего не подходит (нормальный результат, кнопка повтора не нужна). `error` — данные не получены вовсе, показываются причина и «Повторить».
4. **Зачем отменять предыдущий запрос при смене фильтров?** Чтобы не тратить сеть на ненужный ответ и чтобы более медленный старый ответ не перезаписал результат нового фильтра (гонка запросов).
5. **Почему после мутации список повторно запрашивается у API?** Источник истины — сервер: он назначает id, нормализует поля и применяет фильтры. Повторный `GET` с текущими фильтрами показывает только подтверждённое состояние, например исчезновение выполненной задачи из выборки `completed=false`.

Дополнительно:

- **Почему одного `AbortController` недостаточно?** Источник данных (тестовый двойник, кэш) может завершить Promise, не отреагировав на сигнал; проверка номера загрузки отбрасывает такой ответ.
- **Что проверяет клиент, а что сервер?** Клиент — для быстрой обратной связи (форма, фильтры, id). Сервер проверяет всё повторно, т. к. клиент можно обойти (например, `curl`).
- **Почему серверный текст выводится через `textContent`?** Название недоверенное; `innerHTML` выполнил бы разметку вроде `<img onerror>` (XSS).

## 7. Вывод

Интерфейс (`dom-app.js`, `task-view.js`) только отображает данные и передаёт события; контроллер (`app-controller.js`) хранит состояние загрузки и вызывает предметный API; `task-api.js` знает маршруты и схему; `api-client.js` отвечает за HTTP. Благодаря этому контроллер проверяется в Node.js без браузера (33 модульные проверки), а связка с реальным API — интеграционными (14).
